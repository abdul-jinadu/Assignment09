Question 1:
If an ArrayList<Movie> were used instead of a HashSet<Movie>, the program would still compile, but it would behave differently from how it behaves now I think. An ArrayList allows duplicates, so calling addMovie("alice", up) twice would store Up twice in Alice's list, which we didn't want. That would quietly corrupt any later calculation, such as counting how many movies Alice has watched or adding to her total viewing time, because the same movie would be counted more than once depending on how many times alice watched it. To prevent this, addMovie would need an extra contains check before every add, and the programmer would have to remember to do it. Which honestly would just be an extra hassle.

A HashSet solves this just by design, adding an element that is already present (according to equals and hashCode) has no effect. This is also why the Movie class overrides both methods, so that two separate objects describing the same movie are treated as the same element.

Question 2:

Both designs do store the same information, a many-to-many relationship between users and movies, but the two are  organized around a different question. The current design (user → movies), makes user-centered questions easy. "What has Alice watched?" is one get("alice"). "What is Alice's total viewing time?" only requires looping over her set and adding up getRunningTime(). Checking hasWatched("alice", matrix) is two lookups, and removing a user or clearing a user's history touches only one entry. The weakness is movie-centered questions. "Who has watched The Matrix?" requires looping over every user and checking each set individually to see who watched it. "What is the most popular movie?" requires scanning every user's set and keeping a running count for each movie to see which one tallies up the most. As the number of users grows, these operations get slower overtime.

The alternative design (movie → users), is where the movie-centered questions become easy. "Who has watched The Matrix?" is a single lookup, and the number of viewers is just the size of the returned set. Finding the most-watched movie is a simple pass over the map comparing set sizes, and even recommendations like "people who watched Up also watched..." are easier to start up if we really wanted to. hasWatched(user, movie) stays fast because it is get(movie).contains(user). The weakness is the opposite of the current design, which is user-centered questions, basically a vice versa. "What has Alice watched?" now requires looping over every movie and testing whether its set contains "alice". Alice's total viewing time requires the same scan. A user who has watched nothing does not appear anywhere in the map, and removing a user means editing every movie's set. 

When it comes to which to choose. The best design depends on the questions you want to ask the most often. A streaming service's "Continue Watching" and "My History" screens favor our current design (user → movies), while analytics for a news panel about popularity favor the (movie → users) design. A real system might maintain both maps, accepting extra memory and the work of keeping them in sync on every update if a person wanted to answer both sides of the coin that bad.
